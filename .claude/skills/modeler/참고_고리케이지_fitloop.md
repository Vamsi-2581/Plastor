# 참고: 고리 케이지(mh.py)·fitloop 자세한 규칙(옛 SKILL.md 에서 옮김, 2026-10-30)

지금 기본 경로는 build.py(둥근 헐·합치기·검사)다. 고리 케이지·fitloop 를 쓸 때만 이 파일을 본다.

## 0단계. 목표 만들기: 트레이싱(`trace.py`)

목표 윤곽은 외부 파일을 그대로 믿지 않고 도면 이미지에서 만든다(들소 3~6차에서 거친 분해선을 그대로 써서 실패).
1. LLM 은 부위 이름과 **거친 다각형**만 그린다(분해선 형식). 픽셀 정밀도는 도구가 맡는다.
2. `python trace.py clusters --spec S.json` → `clusters.png` 를 보고 `groups_ref`(재질별 기준색: 뿔 밝은 면·그림자 면을 한 재질로 등)를 정한다. 이 묶음이 LLM 판단이다.
3. `python trace.py build --spec S.json` → 배경 먼저 지우기(가장자리와 이어진 배경색 + 회색 안내선) → 전경 색 군집 → 재질 → 작은 얼룩 흡수 → 영역 선택(다각형 안 + 재질 경계로 닫힌 바깥 주머니, 같은 재질이 계속 밖으로 가는 곳만 LLM 선이 컷) → 대칭 뷰는 왼쪽 절반 거울 → `masks.npz`·`profile.json`·`overlay.png`.
4. **뒤 뷰는 새로 그리지 않는다**(`back_from_front`). 한 부위의 정사영은 앞과 뒤가 좌우 거울로 같다. 도면 뒤 컷은 정면과 비교해 불일치만 보고한다(들소: IoU 0.75~0.82).
5. `overlay.png` 를 **직접 본다.** 재질 경계 지지율·G0 는 같은 이미지 경계를 쓰므로 독립 검증이 아니다.
6. 팩의 `files.profile` 을 새 `profile.json` 으로 바꾸고, roi 는 정면·옆 윤곽이 모두 있는 높이로 정한다.

## 1단계. 만들기: 고리 케이지(`mh.py`)

## 핵심

- 너는 **좌표를 쓰지 않는다.** 명령 인자는 이름(랜드마크·부위·뷰), 높이 범위(`--z a b`), 상대값(둥글기 `--n`, 폭 `--width`, 강도 `--strength`)뿐이다.
  도면 위치는 도구가 도면에서 계산해 준다. 모델에서 정점을 찾는 규칙도 도면과 똑같다.
- 모든 명령은 끝에 **측정 보고**(숫자)를 돌려준다. 그림보다 숫자를 먼저 읽는다.
- 판정은 PASS·FAIL·UNKNOWN·ERROR 넷뿐이다. **통과는 `gate` 가 낸 PASS(끝 코드 0)로만** 생긴다. "된 것 같다"는 통과가 아니다.
- 성공 조건(관문 값)을 실패에 맞춰 바꾸지 않는다. 바꾸려면 사용자 승인.

## 실행

```bash
PY="C:/Program Files/Blender Foundation/Blender 5.2/5.2/python/bin/python.exe"
"$PY" mh.py <명령> --session sessions/<이름> ...
```
(시스템 Python 없음. Blender 번들 Python + numpy 만 쓴다. Eevee 렌더만 `blender -b`.)

## G0 목표 검증 (먼저 본다)

G1~G4 는 "모델이 목표에 맞는가"만 본다. 목표(팩 윤곽)가 도면과 다르면 숫자가 전부 PASS 여도 도면과는 다르다(들소 머리 3~6차에서 실제로 겪음: 분해선 다각형이 거칠게 오려져 있었다).
- `G0` 는 목표 윤곽의 점이 **도면 이미지의 색 경계 위**에 있는 비율을 잰다. 80% 이상 PASS, 50% 미만 FAIL, 사이는 UNKNOWN.
- **G0 가 PASS 가 아니면 G1~G4 의 PASS 는 UNKNOWN 으로 내려간다.** 이때는 모델을 고치지 말고 목표(팩)를 고친다: 도면 이미지에서 윤곽을 다시 뽑거나, 사람에게 컷 선을 확인받는다.
- 한계: 머리와 목처럼 원래 경계가 없는 곳을 자르는 선도 "지지 없음"으로 나온다. 그런 컷은 사람이 승인하고 보고에 적는다.
- 판정 전에 **도면 위에 모델 윤곽을 겹친 그림을 직접 본다**(`show`). 숫자와 그림이 다르면 그림이 맞다.

## 작업 순서 (설계서 10절)

1. `pack-build`(한 번) → `init --pack packs/<이름>/pack.json --session sessions/<이름>` → `gate G1`.
   init 직후는 윤곽에서 바로 만든 블록아웃이라 G1 이 대부분 통과해야 정상이다. 안 되면 팩(도면 데이터)을 의심한다.
2. `measure` 의 **최악 5개(수리 대기열)** 를 읽는다. 항목마다 `stage·failure·measured_delta·부위·고리·proposed_action·acceptance_gate` 가 있다.
3. 명령 **하나**를 고른다. 추천(`proposed_action`)은 규칙 기반 제안이다. 따를지는 네가 정한다.
4. 보고를 읽고 반복한다. 한 번에 여러 개를 고치지 않는다(어느 명령이 무엇을 바꿨는지 알 수 있게).
5. 관문 순서: **G1 블록아웃 → G2 랜드마크 → G3 부피 → G4 마감.** 앞 관문이 PASS 여야 다음으로 간다.
6. `show`(겹침 그림)는 관문 통과 직후와 사람에게 보여 줄 때만 본다. 평소에는 보지 않는다. 그림을 보고 값을 눈대중으로 고치지 않는다.
7. **같은 관문에서 명령 12개를 써도 PASS 가 안 나오면 멈추고** 남은 오차를 사람에게 보고한다. 같은 관문에서 구조를 두 번 고쳐도 FAIL 이어도 멈춘다.

## 명령 (손)

| 명령 | 하는 일 | 값 범위(벗어나면 ERROR) |
|---|---|---|
| `init --pack P [--rings R] [--z a b]` | 윤곽 행에서 고리 생성 | n 1.6~5 |
| `fit --view front\|side\|back\|width [--z a b] [--strength s] [--blend k]` | 높이 범위 고리의 반폭/앞끝·뒤끝을 도면 윤곽으로 | strength 0~1 |
| `snap <랜드마크> [--falloff r]` | 같은 규칙으로 모델 정점을 찾아 도면 위치로 끌고, 주변은 코사인 감쇠 | falloff 0.05~0.6 |
| `round --z a b --n v` | 단면 둥글기. 정면·옆 윤곽은 그대로, 3/4 부피만 변함 | n 1.6~5 |
| `narrow --part 이름 \| --z a b  --width v \| --from-landmark 이름` | 앞쪽 폭 배수(주둥이 좁히기). 최대 폭 점은 그대로 | width 0.3~1.5 |
| `shift --z a b [--dy v] [--tilt deg]` | 고리 중심 이동·기울이기 | |
| `add_ring --z v` / `remove_ring --i k` | 고리 추가·삭제(값 보간) | |
| `smooth --z a b [--k s]` | 평활(윤곽이 변하므로 뒤에 `fit`) | k 0~1 |
| `undo` / `goto vNNN` / `log` | 되돌리기·이동·기록 | |
| `measure [--full]` / `gate G1..G4\|all` / `show` / `export` | 보고·판정·그림·내보내기 | |

`--view width` 는 정면과 뒤 도면 반폭의 **평균**에 맞춘다. 모델은 좌우 대칭이라 정면과 뒤 실루엣이 같을 수밖에 없는데, 도면은 둘이 달라서(최대 0.08H) 한쪽에만 맞추면 다른 쪽 띠 오차가 커진다.

## 규칙 (모델러의 판단)

- **순서가 중요하다.** `snap` 은 맨 끝에 한다. `fit`·`round`·`narrow`·`smooth` 가 정점을 움직이면 snap 한 위치가 어긋난다. `snap` 뒤에 `fit` 을 하면 끌어 놓은 점이 도로 당겨진다.
- **구조 문제는 네 몫이다.** 한 고리로 표현이 안 되는 곳(턱 밑 단차, 입 선)은 `add_ring` 으로 고리를 더하거나 부위를 나눈다. 숫자를 더 비틀어 억지로 맞추지 않는다.
- `round` 는 윤곽을 안 바꾼다. 윤곽이 맞는데 3/4 부피가 이상하면 `round`·`narrow` 로 고친다. 윤곽이 틀리면 `fit`.
- `narrow` 는 3/4 비율을 낮춘다(앞이 좁아지므로). G3 가 낮게 나오면 `round` 로 n 을 올려 균형을 본다. G3 구간(0.80~0.92)은 **가설**이다. FAIL 이어도 수치를 그대로 보고하고 구간을 몰래 바꾸지 않는다.
- 도면 정면·뒤 불일치, 도면 높이 불일치(눈) 같은 **도면 자체의 문제**는 수정 대상이 아니라 보고 대상이다.
- 값 범위 밖 요청은 ERROR 로 거부된다. 범위를 넓히려 하지 말고 다른 명령을 고른다.

## 하지 않는 것

- 정점 좌표·픽셀 좌표를 직접 적지 않는다. (`manual` 랜드마크의 픽셀은 팩 작성 단계에서만 쓰고 신뢰도를 표시한다. 눈·코 폭 같은 실루엣 밖 내부 특징에만.)
- 관문 값(`gates.json`)을 결과에 맞춰 고치지 않는다.
- 뿔·귀는 별도 부품이다(이 버전 범위 밖).
- 옛 머리와 비교할 때(`compare-obj`) 옛 머리의 앞뒤 위치를 아는 척하지 않는다. 확정 못 하면 UNKNOWN 으로 적는다.

## 보고 형식 (사람에게)

판정표(G1~G4 와 값), 명령 수, 남은 오차(부위 이름 포함), 도면 자체 불일치, 한 일 중 설계와 다르게 한 점. 모두 한국어. 수치는 실행 결과 그대로 옮기고 지어내지 않는다.

## 2단계. 다듬기: fitloop(`fitloop.py`)

## 원칙

- **너는 좌표를 쓰지 않는다.** 쓰는 것은 이름(핸들·지표), 규칙(극점 방향·높이 창), 상대값(반경, 단계 비율)뿐이다. 목표 위치는 도면 마스크에서 도구가 읽고, 메시 쪽 점도 같은 규칙으로 도구가 찾는다.
- **판정은 PASS·FAIL·UNKNOWN·ERROR 뿐이다.** 통과는 `tests/selftest.py` 끝 코드 0, 또는 수치 조건을 실행으로 확인한 것만 센다. "맞아 보인다"는 통과가 아니다.
- 눈대중 수정으로 실패를 우회하지 않는다. 안 맞으면 멈추고 남은 오차와 원인 후보를 보고한다.
- 새 설치·MCP 없이 Blender 5.2 + numpy 로만 한다(필요해지면 사용자 승인).

## 실행 (Blender 안에서만 돈다)

```bash
B="C:/Program Files/Blender Foundation/Blender 5.2/blender.exe"
"$B" -b -P fitloop.py -- doctor                 # 환경 검사
"$B" -b -P fitloop.py -- attach spec.json       # OBJ → 규칙으로 정점 그룹 → 핸들 → step00.blend
"$B" -b -P fitloop.py -- run spec.json          # 측정·민감도·이동·재측정 반복
"$B" -b -P fitloop.py -- hash 파일.blend 메시이름   # 체크포인트 복원 검증
```
자체 시험: `"C:/Program Files/Blender Foundation/Blender 5.2/5.2/python/bin/python.exe" tests/selftest.py` (끝 코드 0 = PASS).

## spec.json 에 쓰는 것 (모두 규칙·이름)

- `frame`: 도면 틀(1H 의 블렌더 길이, px_per_H, 발바닥 행, 이미지 크기, 패널별 중심선 x). **도면 등록 파일(trace_meta)에서 옮겨 적는다.** 눈으로 읽지 않는다.
- `target_masks`: 패널별 목표 실루엣 마스크(.npy).
- `handles`: `kind` hook|lattice, `axes`, `select`(극점 규칙 + 반경/상자 크기). 정점 번호를 적지 않는다.
- `metrics`: 맞출 지표(`extreme` 극점의 가로·높이, `edge` 윤곽 끝, `width` 폭). `protected`: 건드리면 안 되는 띠. `report`: 보고만 하는 IoU 띠.
- `step_frac`(한 걸음에 옮기는 비율, 기본 0.5), `tol`, `max_steps`(기본 10).

## 순서

1. `doctor` 가 PASS 인지 본다.
2. 핸들은 **부위를 통째로 움직이도록** 만든다. Hook 반경이 작으면 극점이 이웃 정점으로 넘어가 지표가 불연속이 된다(이번 시험에서 실제로 겪음). 반경·상자는 움직일 덩어리(돌기·주둥이) 전체를 덮는다.
3. `attach` → 보고의 `핸들_연결_후_변화` 가 0 이고 핸들마다 정점 수·bbox 가 합리적인지 본다.
4. `run` → `steps.jsonl` 에서 걸음마다 `수정전_오차 → 이동량 → 수정후_오차` 를 읽는다. 오차가 늘면 `민감도_J` 를 본다(0 인 열 = 그 핸들이 지표에 안 보인다 = 지표나 핸들 설계 문제).
5. 부작용 항목(`대상밖_띠_오차_증가`, `IoU_전→후`, `메시_전→후`)이 나빠지면 그 걸음의 체크포인트(`stepNN.blend`)로 돌아가 원인을 본다.
6. **10걸음 안에 안 줄면 멈춘다.** 같은 핸들·지표 구성을 두 번 고쳐도 안 되면 멈추고 보고한다.

## 알아 둘 한계 (보고에 그대로 쓴다)

- 정밀도는 도면 픽셀 크기(1/px_per_H H)가 한계다. 민감도 걸음은 그보다 충분히 커야 지표가 변한다(기본 약 8픽셀).
- 실루엣만 본다. 실루엣 안쪽 특징(눈·코 영역 색)은 이 단계에서 못 잰다.
- 한 뷰에서만 보이는 축은 움직이지 않고 UNKNOWN 으로 둔다.
- 대상 밖 보존 검사는 보호 띠를 어디에 두었는지에 달렸다. 핸들 영향 범위 근처에도 보호 띠를 둔다.
- 들소에는 아직 돌려 본 적이 없다(1→2단계 연결은 UNKNOWN).

## 보고 형식 (사람에게, 한국어)

판정표, 걸음 수, 시작→최종 오차, 되찾은 이동량, 부작용, 실패·UNKNOWN 과 이유. 수치는 실행 결과 그대로 옮기고 지어내지 않는다.

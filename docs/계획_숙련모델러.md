# 계획: Claude Code 를 숙련 3D 모델러로 동작하게 하기 (2026-10-29)

> 2026-10-30: 실행 계획의 기준은 `docs/구현계획_통합.md`(K1~K9)로 옮겼다. 이 문서는 배경·기록이다.

사용자 요청: "우리가 클로드 코드를 숙련된 3d 모델러로서 동작하게 할 방법을 계획해봐."
관련 문서: `docs/설계_LLM_3D모델러.md`(틀·로드맵 R1~R8, 6장 숙련 모델러), `docs/설계도_형식.md`, `docs/설계_형태판단.md`, `docs/조사_색인.md`.

## 0. 한 줄 요약
Claude Code 가 코딩을 잘하는 건 "파일·명령·시험·기록" 틀 덕분이다. 숙련 모델러도 같은 틀로 만든다: **설계도(머릿속 계획을 글로) → 공정 순서(큰 것부터) → 모델러 연산(좌표 없이 부위 단위) → 눈(고정 시점 그림) → 비평(항목별, 두 가족) → 기억(교훈·절차 카드)**. 모델은 바꾸지 않고, 틀만 숙련자의 일하는 방식으로 바꾼다.

## 1. 숙련자와 지금 하네스의 차이
| 숙련 모델러가 하는 것 | 지금 하네스 | 빈칸 |
|---|---|---|
| 그리기 전에 형태를 읽는다(무엇이 공이고 관인지, 뼈대·비율) | 트레이싱 → 헐 | 설계도 단계가 없다(형식만 초안) |
| 큰 덩어리 → 1차 → 2차 → 세부 순서, 앞이 틀리면 뒤를 안 함 | 카드 1~5(뷰·큰 형태·부위·합치기·리깅) | "세부"와 "아트" 단계가 없다 |
| 부위별로 만들고 따로 고친다 | 부위 헐을 한 번에 | 부위 단위 연산 없음(R2) |
| 수시로 돌려 보고, 작게 줄여 실루엣을 본다 | 3/4·위·아래 그림 | 축소 실루엣·도면 겹쳐 보기 없음 |
| 아트 원칙(비율·형태 언어·큰-중-작)으로 스스로 비평 | 재투영 IoU 같은 충실도만 | 그럴듯함·아트 검사기 없음(R4) |
| 도면 오류는 알아보고 무시 | 그림 모순 기록만 | 의도 파악 루프 미구현(R2.5) |
| 경험이 쌓인다 | 교훈 jsonl·카드 | 공정별 절차 지식이 얇다 |

## 2. 구조: 여섯 부품
1. **설계도 먼저**(`blueprint` 도구): 트레이싱과 도구 측정으로 숫자를 채우고, LLM 은 이름·종류·짝·붙는 곳·그림 모순 결정만 쓴다(`docs/설계도_형식.md`). 설계도 검사가 PASS 여야 메시를 만든다.
2. **공정 상태 기계**(카드 재편): `0 읽기(설계도)` → `1 블록아웃(큰 덩어리·비율)` → `2 1차 형태(실루엣·주요 면)` → `3 2차 형태(부위·덩어리 이음)` → `4 합치기·세부` → `5 리깅 준비` → (뒤에 텍스처·리토폴로지). 단계마다 관문 하나, 앞 관문 FAIL 이면 뒤 카드 안 나옴(지금 규칙 그대로).
3. **모델러 연산**(좌표 없음, 부위·상대값만): `part_add(이름, 종류)`, `section_set(부위, t, 모양 틀)`, `scale_rel(부위, 폭 +10%)`, `attach(부위, 부모, 자리)`, `mirror(부위)`, `rebuild(부위)`, `smooth(부위, 강도 단계)`. 한 부위를 고치면 다른 부위 지문은 그대로여야 한다(R2 기준).
4. **눈**(`look` 도구): 고정 시점 묶음 = 정면·옆 도면 겹침, 3/4 두 개, 위, **64px 검은 실루엣**, 면 음영(무늬 없는 회색). 그림은 관문 때만 본다(비용 규칙).
5. **비평**(`critique` 도구): 항목별 점수, 통째 "좋은가"는 묻지 않음. 항목: 실루엣 읽힘·비율(설계도 대비)·형태 언어 일관·큰-중-작 대비·무게감/접지·대칭·도면 스타일. 가능한 항목은 **숫자 대리값 먼저**(비율 = 설계도 측정, 형태 언어 = 곡률 분포·단면 초타원 지수, 실루엣 = 축소 IoU), 숫자로 못 재는 것만 두 모델 가족(Claude 하위 에이전트 Sonnet + Codex, 보기 순서 바꿈). 비평은 단계당 최대 3바퀴(Planner-Actor-Critic: 3번쯤에서 더 안 좋아짐), 그다음은 조사 단계 또는 UNKNOWN 으로 사람에게.
6. **기억**: 단계 카드(정 → 동) + 교훈 + **절차 카드**(튜토리얼·숙련자 공정에서 뽑은 "크리처 머리 블록아웃 순서" 같은 것, 출처 적고 사람이 한 번 검토). 결과 장부(R8)에 과제·모델·설정·판정을 쌓는다.

규칙: 도면 > 아트 판단. 아트 판단은 도면이 말하지 않는 곳(뒤·안쪽·단면·세부)과 그림 모순 판정 근거로만 쓴다.

## 3. Claude Code 안에서의 배치
- **입구**: 스킬 `modeler` 를 공정 순서로 다시 쓴다(지금 175줄 → 짧은 본문 + 단계 카드 참조). 사용자는 "이 도면으로 만들어"만 말한다.
- **역할**: 주 세션(계획·결정) / 도구(측정·만들기·검사, 판정은 여기서만 나옴) / 하위 에이전트 Sonnet(비평·피아식별, 동시 2개) / Codex(엇갈릴 때 두 번째 가족).
- **훅**(선택, 승인 필요): 보고에 PASS 라고 쓸 때 해당 도구 결과 파일이 있는지 확인하는 Stop 훅, 도구 호출을 장부에 남기는 PostToolUse 훅.
- **도구 층**: 지금 `mh_tool.py`(CLI)를 그대로 늘린다(blueprint·look·critique·연산들). MCP 서버로 바꾸는 건 나중 선택(승인 필요).

## 4. 순서(각 단계 채택 기준은 돌리기 전에 정함)
| 단계 | 할 일 | 채택 기준 |
|---|---|---|
| M0 과제 묶음 먼저 | 합성 크리처 6종(정답 메시 있음) + 케라투라 머리 3종(들소·새·하나 더). 비교 기준선: ① 하네스 없이 Claude Code + Blender MCP 자유 작업 ② 지금 하네스 | 같은 과제를 다시 돌리면 같은 결과(지문). 기준선 두 개의 점수가 장부에 있음 |
| M1 설계도 + 공정 카드 | `blueprint` 도구·검사, 카드 0~2 재편 | 합성 6종에서 설계도만으로 만든 모델의 재투영 IoU ≥ 둥근 헐 − 0.01, 부피 IoU > 둥근 헐 |
| M2 모델러 연산 | 부위 단위 연산 7개(R2) | 부위 하나를 바꾸면 다른 부위 지문 같음(시험), 들소 단계 1~5 판정 유지 |
| M3 형상 | R1 매끈한 일반화 원통 + R1.5 이름 → 단면 틀 | 로드맵 R1·R1.5 기준 |
| M4 눈과 비평 | `look`·`critique`, 숫자 대리값 + 두 가족 | 좋은 판과 일부러 망친 판(비율·실루엣·형태 언어)을 항목 점수가 가려냄(두 가족 일치 ≥ 0.8), 들소 16차 각진 머리를 형태 언어 항목에서 낮게 잡음 |
| M5 의도 파악 | R2.5(`docs/구현안내_의도파악루프.md`) | 그 문서 4단계 기준 |
| M6 끝까지 | 텍스처(R5)·리토폴로지·리깅(R6) | 로드맵 기준 |
| **최종 판정** | M0 과제 묶음 전체를 다시 | 지금 하네스 대비 과제 평균: 재투영 IoU 하락 없음 **그리고** 아트 항목 중 셋 이상 개선(두 가족 일치), 사람이 본 6장 비교에서 "더 낫다"가 과반. 못 미치면 FAIL 로 적고 원인 분류 |

순서 이유: M0 이 없으면 "숙련자처럼 됐는지"를 잴 수 없다. M1·M2 는 숙련자의 "계획하고 부위로 고치기", M3 은 지금 가장 눈에 띄는 문제(각진 모양), M4 는 사람 눈 없이 아트를 재는 장치다.

## 5. 위험과 모르는 것
- 두 가족 아트 판정이 셀 셰이딩 크리처에서 믿을 만한지 UNKNOWN(Laya Vision 0.53 전례). 숫자 대리값을 먼저 두는 이유.
- 튜토리얼 영상에서 절차 뽑기(BlenderLore 식)는 원 저장소를 확인하지 못했다. 처음엔 사람이 검토한 절차 카드 몇 장으로 대신한다.
- 비용: 주간 사용량이 멈춤 선 근처. 비평은 관문 때만, 하위 에이전트 Sonnet, Codex 는 엇갈릴 때만.

## 6. M0 실행 기록(돌리기 전에 적음, 2026-10-29)
- 과제(`bench/m0/`, 도구 `bench/m0.py`): 합성 6종(씨앗 600~605, 개발에 안 쓴 씨앗: 기본·색조·두 재질 귀·체크무늬·배경 비슷한 뿔·외곽선), 실제 2종(들소 머리, 새 머리). 세 번째 실제 머리는 아직 없음(새 고정물 필요, 남은 일).
- 채점: 실루엣 IoU(정면·옆, 합성은 정답 마스크·실제는 하네스 트레이스 대비라 **정답 아님**), 부피 IoU(합성만, 0.01H 복셀, 정답 타원체 합집합에서 목 제외), 합친 메시 몸 수, 지문. 장부 `bench/m0/ledger.jsonl`.
- 기준선 ② 지금 하네스: `m0.py harness`, 들소 16차 설정(본체 둥근 헐 + 제한 이완 20, 뿔류 둥근 헐, 나머지 헐, 박기, 합치기 0.06). 손대지 않고 한 번에 돌린 결과만 적는다.
- 기준선 ① 하네스 없는 자유 작업: 하위 에이전트(Sonnet) 하나에 도면 PNG·축척(1H 픽셀·중심선·발바닥 행)만 주고, Blender 헤드리스 파이썬으로 OBJ(H 단위)를 만들게 한다. 하네스 코드(trace·build·harness/)는 쓰지 못한다. 자기 렌더로 고치기 최대 3번. 비용 때문에 합성 2종(기본·체크무늬)부터.
- M0 채택 기준(계획 4장): 같은 과제를 다시 돌리면 같은 지문, 기준선 두 개의 점수가 장부에 있음. 둘 다 되면 PASS, 기준선 ①이 2종뿐이면 그 범위로만 적는다.

- **판정 FAIL**(돌리기 전 기준): 재현성이 합성 기본은 같은 지문(PASS)이지만 새 머리는 다시 돌리니 지문이 달라짐(7388342fd866 → e45582cbd923, 몸 수 1 → 2, 원인 UNKNOWN). 기준선 ① 은 합성 2종만(범위 좁음).
- 읽은 것: 하네스는 **실루엣이 더 맞고(정면 +0.05~0.08) 부피는 크게 나쁘다(−0.29~−0.46)**. 두 뷰 헐이 깊이 방향을 부풀리는 '각진 모양' 문제를 숫자로 확인. 단, 정답이 타원체이고 기준선 ① 도 타원체로 만들어 ① 에 유리한 과제다(합성 정답의 한계). 체크무늬·외곽선·두 재질에서 옆 실루엣이 0.80~0.84 로 떨어지고 떠 있는 조각이 많다(몸 수 최대 36).
- 이 과정에서 찾아 고친 하네스 버그: 합집합이 본체를 지움(수정_기록 44). 채점기 고침: 겹친 조각별 복셀화, 축척 맞춘 복셀(새 머리 0.62 → 0.98 은 채점기 문제였음).
- 다음: 새 머리 비결정성 원인 찾기(M0 재판정), 그다음 M3(형상)이 가장 급함. 실루엣을 지키며 부피를 올리는 것이 M1·M3 채택 기준의 핵심.

### 6.2 M0 재판정(숨은 입력 고친 뒤, 수정_기록 45)
- **판정 PASS(범위: 기준선 ① 은 합성 2종만)**: 과제 8개를 두 번 돌려 지문 8개 모두 같음, 기준선 두 개 점수가 장부에 있음. 빌드 자체 시험 9개 PASS.
- 최종 점수(장부 마지막 줄): ② 하네스 합성 6종 실루엣 정면 0.883~0.971 / 옆 0.807~0.978, 부피 0.385~0.634, 몸 수 4~14. 실제 들소 0.977/0.926, 새 머리 0.985/0.924(트레이스 대비), 몸 수 1. ① 자유 합성 2종 실루엣 0.878~0.885 / 0.898~0.902, 부피 0.732~0.898.
- 결론은 6.1 과 같다: 하네스는 실루엣이 낫고 부피가 크게 나쁘다. 떠 있는 조각(몸 수 > 1)이 합성 전부에 있다. 다음은 M3(형상)과 떠 있는 조각.

## 7. 스스로 판단하는 분기 루프(`bench/auto_loop.py`, 계획 `bench/loop/plan.json`)
- 분기는 미리 적은 기준과 측정 숫자로만(루프 안에 LLM 없음). 개발 과제(씨앗 700~705)로 고르고 M0 과제(600~605)로 확인. 모든 후보가 떨어지면 `bench/loop/판단_필요.md` 를 남기고 멈춘다(조사·새 후보는 LLM).
- 첫 항목 '단면틀'(R1.5 이름 → 단면 틀의 첫 걸음): 높이별 단면을 직사각형 대신 꽉 찬 초타원으로(`harness/hull.section_fill`). 기준: 개발·확인 모두 평균 부피 ≥ 기준선 + 0.05, 평균 실루엣 ≥ 기준선 − 0.01. 후보 5개(본체 n=2·2.5·3·덜 다듬기, 전부 n=2).

## 9. 진단 정정과 Rust 로 완성하는 길(2026-10-30)
- 정정(수정_기록 46): 부피 손실은 가림만이 아니다. 뿔은 둥근 헐이 정답의 절반만 덮음(IoU 0.33~0.35, 그냥 헐 0.60~0.62), 머리는 가려진 20~30% 를 헐이 못 채우고 무작정 채우면 부풀음. 둘 다 "도면에 보이는 것만으로는 정해지지 않는 곳을 형태 지식으로 채우는" 문제 → 숙련 모델러의 일.
- 구조: LLM = 설계도(부위 이름·연산자 종류·붙는 곳·짝·그림 모순), Rust = 연산자 + 맞추기기 + 조립 + 채점, Blender = 마감(내보내기·리깅), 하네스 = 판정(M0·루프).
- Rust 연산자: 초타원체 덩어리(머리·주둥이·몸), 휜 관(중심선 곡선 + 반지름 변화 + 초타원 단면: 뿔·꼬리·다리), 판(귀·지느러미). 모두 부호 거리장(SDF).
- 맞추기: 매개변수 수십 개를 미분 없는 최적화(좌표 하강·CMA-ES 류, CPU)로. 손실 = 보이는 픽셀 불일치 + 가려진 픽셀은 '상관없음' + 대칭·매끈함 벌점. Rust 라 평가 한 번이 수 ms.
- 조립: 부위 SDF 의 합집합(최솟값, 부드러운 이음은 smooth-min)을 한 번에 표면 뽑기 → 늘 한 덩어리, 불리언 실패(수정_기록 44) 같은 문제가 구조적으로 없음.
- 단계와 기준(돌리기 전): S1 뿔 관 맞추기(안 본 씨앗 뿔 실루엣 ≥ 0.95, 부피 IoU ≥ 0.80), S2 머리 덩어리 맞추기(머리 부피 IoU ≥ 0.80), S3 SDF 조립(몸 수 1, 합친 실루엣 하락 ≤ 0.01), S4 LLM 설계도 → 연산자 → M0 확인 과제 부피 ≥ 0.80·실루엣 ≥ 0.95, S5 실제 도면 사람 확인 + Blender 내보내기·리깅.

### 9.1 S1 뿔 관 맞추기: 측정 정의와 기준(돌리기 전, 2026-10-30)
- 대상: 뿔 = 트레이스의 '뿔' ∪ '뿔 밑동'. 좌우 한 쌍(거울). 입력은 하네스 트레이스 마스크(정답 아님), 채점은 정답.
- 부위 실루엣 IoU: 뷰마다 정답 뿔 마스크와 모델 투영을 비교하되, **정답에서 다른 부위로 보이는 픽셀은 뺀다**(뿔이 그 뒤에 있을 수 있어 옳고 그름을 모름). 정면·옆 평균.
- 부위 부피 IoU: 0.01H 칸, 정답 = 뿔·뿔 밑동 타원체 합집합.
- 비교: 그냥 헐(스무딩 1.5), 하네스 둥근 헐(M0 기준선 `part_뿔.obj`+`part_뿔 밑동.obj`), 관 맞추기.
- 과제: 개발 dev_* 6종(씨앗 700~705, 고치는 데 씀), 확인 synth_* 6종(M0 600~605, 판정에만).
- **PASS**: 확인 과제 평균 실루엣 ≥ 0.95 그리고 평균 부피 IoU ≥ 0.80. 그 밖 FAIL.
- 주의(결과 해석): 합성 뿔은 구를 이은 사슬이라 '원 단면 관'과 같은 모양 가족이다. 합성에서 좋게 나올 쪽으로 치우친 과제이므로, PASS 해도 실제 도면(들소 뿔)은 그림으로 따로 확인한다.

### 9.2 크로스 컨투어(톤 띠 경계)를 맞추기에 넣기(사용자 "크로스 컨투어 라인을 사용할 거라고 하지 않았냐", 2026-10-30)
- 빠졌던 것: R1.5(셀 셰이딩 톤 띠 경계 = 같은 밝기 선 → 면 방향)는 로드맵·설계도 형식에만 있고 S1~S5 실행 단계에 연결되지 않았다. 여기서 연결한다.
- 원리: 실루엣은 앞뒤 깊이를 못 정한다(머리가 헐의 70~79% 만 덮음). 톤 띠 경계는 n·L = 문턱 인 선이라 실루엣 **안쪽**의 면 방향을 준다. 맞추기 손실에 '톤 띠 불일치'를 더한다: 모델을 같은 빛·같은 문턱으로 셀 셰이딩해 비추고, 그 부위가 보이는 픽셀에서 띠 번호(0·1·2)가 도면과 다른 픽셀 수.
- 필요한 것: (가) 트레이스가 이미 재는 톤 지도(재질별 3톤, `tone_cut`), (나) 빛 방향: 합성은 알고(L=(0.45,0.55,0.7), 문턱 0.55·0.15) 실제 도면은 추정(R1.5: 띠 경계 법선으로 빛 방향 맞추기, 뷰마다 다르면 그림 모순 근거), (다) Rust 셀 셰이딩 투영(맞추기 안쪽에서 수 ms).
- 단계에 넣음:
  - **S1b**(S1 뒤): 뿔 단면 초타원 지수·납작함을 톤 띠로 정함. 기준: 톤 항을 켠 것이 끈 것보다 확인 과제 뿔 부피 IoU 가 높고 실루엣 하락 ≤ 0.005.
  - **S2**(머리): 톤 항을 처음부터 손실에 넣는다. 기준(돌리기 전): 확인 과제 머리 부피 IoU ≥ 0.80, 그리고 톤 항 켬 − 끔 ≥ +0.03(톤이 실제로 깊이를 잡는다는 반증 가능한 예측). 끔 − 켬 차가 0.03 미만이면 '톤 항 효과 없음'으로 FAIL 기록.
  - **R1.5 빛 방향 추정**: S2 를 실제 도면에 쓰기 전 관문. 합성에서 빛 방향 오차 ≤ 10°(설계도 형식 문서 기준 그대로).
- 주의: 합성은 렌더러와 맞추기의 셀 셰이딩 식이 같아 유리하다. 실제 도면은 손그림 톤이라 문턱·빛이 부위마다 다를 수 있다 → 실제 도면에서는 톤 항 가중치를 낮게 시작하고 그림으로 확인.

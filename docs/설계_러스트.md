# 설계: 도구를 Rust 로 (2026-10-29)

사용자 요청: "도구 전체를 러스트로 설계해서 구현해, 마이그레이션할 게 있으면 하고".
목표 한 줄: **하네스의 계산과 도구 층을 Rust 바이너리 `mh` 하나로 옮긴다. Blender 안에서 도는 일과 학습 모델만 파이썬으로 남긴다. 옮긴 것마다 파이썬판과 결과가 같은지 대조 시험으로 확인한 뒤에만 바꿔 쓴다.**

## 1. 옮길 수 없는 것(파이썬으로 남음)과 이유
| 부분 | 파일 | 이유 |
|---|---|---|
| Blender 안의 일 | `harness/blender_merge.py`, `blender_view_bg.py`, `rig_check.py`, `fitloop.py`, `blender_daemon.py`, `bench/npy2png.py` | Blender 는 파이썬(`bpy`)으로만 조작된다. Rust 는 `blender -b -P 스크립트 -- 인자` 로 부르고 표준출력의 `MERGE ...` 같은 줄을 읽는다(지금과 같음) |
| 학습 모델 | `tools/sam_worker.py`(SAM 2.1), Laya, ToonOut | torch·transformers 가 파이썬. Rust 는 일꾼 프로세스로 부르고 npz/JSON 으로 주고받는다 |
| 합성 장면 렌더 | `bench/scene.py`(numpy 셀 셰이딩) | 정답을 만드는 기준이라 마지막에 옮긴다(옮기면 정답 자체가 바뀔 수 있음, 지문으로 확인) |

## 2. 구조
```
rust/                      Cargo 작업 공간
  mh-core/   격자·마스크(npy/npz 읽기·쓰기)·좌표틀(팩·meta)·형태 연산(연결 성분, 팽창, 구멍 메우기, 거리 변환, 가우시안)·메시(OBJ)·표면 뽑기
  mh-geom/   헐(직사각형·초타원 단면), 부위 박기, 둥근 헐(쓸기·실루엣 채우기), 제한 이완
  mh-check/  복셀화·재투영·IoU·가림·진단(그림 모순·모델링 오차·상자 단면·떠 있는 조각), 합친 메시 검사, M0 채점
  mh-trace/  배경 견본·Lab k-means·영역 선택·겹침 해소(3단계)
  mh/        바이너리: 도구 층(JSON 입출력, 끝 코드 PASS 0·FAIL 1·UNKNOWN 2·ERROR 3), build 파이프라인, 루프 엔진, Blender·SAM 부르기
```
- 도구 약속은 지금과 같다: 받는 값에 좌표 없음, 결과는 `{판정, 요약, 파일}`. LLM 쪽에서 보면 `mh_tool.py <도구> '<JSON>'` 이 `mh <도구> '<JSON>'` 로 바뀔 뿐이다.
- 파일 형식은 그대로 둔다(masks.npz, build.json, build_steps.json, OBJ, 장부 jsonl). 그래서 단계별로 섞어 쓸 수 있다.
- 라이브러리는 최소로: `serde_json`(JSON), `zip`(npz 압축). 수치 연산은 직접 짠다(numpy·scipy·skimage 를 대신할 크레이트를 끌어오지 않음).
- 표면 뽑기: skimage 의 Lewiner marching cubes 를 그대로 옮기지 않고 **표 없이 맞출 수 있는 marching tetrahedra**(정육면체를 사면체 6개로) 를 쓴다. 메시 모양이 조금 다르므로 대조는 지문이 아니라 복셀 IoU 로 한다.

## 3. 단계(각 단계 채택 기준은 돌리기 전에 정함)
| 단계 | 옮길 것 | 채택 기준(파이썬판과 대조) |
|---|---|---|
| P1 계산 핵심 | npy/npz, 좌표틀, 복셀화, 재투영, IoU, 헐(직사각형·초타원), 가우시안, 표면 뽑기, OBJ. 명령 `mh voxsil`, `mh hull` | 같은 OBJ 의 복셀화 결과가 **칸 단위로 같음**(파이썬 `model_check.voxelize`), 재투영 IoU 차 0. 같은 마스크로 만든 헐의 복셀 IoU ≥ 0.99, 실루엣 IoU 차 ≤ 0.005. 속도 기록 |
| P2 파이프라인 | `build` 단계 body·parts·check·merge 부르기, 박기, 합친 메시 검사, 카드 | `tests/selftest_build.py` 와 같은 9개 검사를 Rust `build` 로 PASS, M0 과제 8개 점수가 파이썬판 ± 0.005 |
| P3 둥근 헐 | 쓸기·실루엣 채우기·제한 이완(cesn) | 들소 16차 설정으로 M0 점수 ± 0.005 |
| P4 트레이싱 | 배경 견본, Lab k-means, 영역 선택, 겹침 해소, SAM 일꾼 부르기 | `tests/selftest_trace.py` 18개 PASS(같은 검사를 Rust 로), 벤치마크 68~79 평균 차 ≤ 0.002 |
| P5 도구 층·루프 | `mh` 도구 7개, 루프 엔진(`bench/auto_loop.py`), M0 채점 | `tests/selftest_api.py` 9개, 루프가 같은 계획에서 같은 판정 |
| P6 정리 | 파이썬 중복 제거, 문서·스킬 명령 바꿈 | 자체 시험 전부 PASS, 사람이 쓰는 명령이 `mh` 로 |

- 옮기는 중에는 파이썬판이 기준(정답)이다. 결과가 다르면 Rust 를 고친다. 파이썬판의 버그를 찾으면 둘 다 고치고 수정_기록에 적는다.
- 순서 이유: P1 이 가장 느린 곳(복셀화가 삼각형마다 파이썬 반복문, 과제 하나 1~2분)이고, 나머지가 모두 P1 위에 선다.

## 4. 대조 시험
- `tests/selftest_rust.py`(파이썬): Rust 바이너리를 부르고 같은 입력을 파이썬 함수에 넣어 비교한다. 끝 코드 0 = PASS.
- 비용 규칙: 빌드는 `cargo build --release`, 시험은 합성 과제 몇 개로.

## 5. P1 결과(2026-10-30)
- **PASS**: `tests/selftest_rust.py` 12개(합성 기본·들소·새 머리 × 복셀화 칸 단위 같음·재투영 같음·헐 직사각형·헐 초타원). 처음 1개 FAIL 은 Rust JSON 이 실수를 마지막 자리까지 정확히 읽지 않아(serde_json 기본) 원점이 1ulp 달랐던 것 → `float_roundtrip` 켬.
- 속도: 복셀화 파이썬 4.0~10.4초 → Rust 0.04~0.06초. 헐은 Rust 가 느림(0.2초 → 0.8초, 가우시안을 단순하게 짬, P2 에서 고칠 것).
- 마이그레이션: `harness/model_check.voxelize` 가 Rust 가 있으면 Rust 를 부른다(메시는 npy 로 넘겨 실수가 그대로, 칸 단위로 같음 확인, 새 머리 13.3초 → 0.13초). `MH_RUST=0` 이면 파이썬판. 3D 검사 자체 시험 13개 PASS.
- 처음엔 크레이트 하나(`rust/`) 안의 모듈로 짰다(2장의 크레이트 나누기는 P2 이후).

## 6. 방향 바뀜(2026-10-30, `docs/구현계획_통합.md`)
- P3(둥근 헐 이식)은 하지 않는다: 둥근 헐이 뿔 정답의 절반만 덮음(수정_기록 46). 대신 K2: 크레이트를 core·sdf·fit·check·tool 로 나누고 SDF 연산자·맞추기·조립을 만든다.

## 7. 결정: 파이썬이 꼭 필요한 곳 말고는 전부 Rust(사용자 2026-10-30 "파이썬이 없으면 안 되는 부분 제외 전부 러스트")

- 옮기는 순서는 진단 보고서 우선순위를 따른다: 버릴 것은 옮기지 않고, 새로 만드는 것은 처음부터 Rust 로.

### 7.1 첫 걸음 기준(돌리기 전, 2026-10-30)
- **PNG**: Rust 가 쓴 PNG 를 Blender 가 읽은 화소가 원래 배열과 칸 단위로 같음(그림 3장).
- **채점기 대조**: M0 과제 10줄(① 2·② 8)을 Rust 채점기로 다시 매긴 값이 장부의 'K1 재채점' 값과: 실루엣 차 ≤ 0.002, 부피 차 ≤ 0.005, 부위 실루엣·부피 차 ≤ 0.005, 3/4 폭 비 차 ≤ 0.01, 거칠기 v2 차 ≤ 0.5°, 랜드마크 잔차 차 ≤ 0.005H, 몸 수 같음. 합성 정답 도형은 파이썬이 만든 것을 한 번 `prims.json` 으로 내보내 쓴다(같은 정답).
- **생성기 v2**: (가) 같은 씨앗 → 같은 파일 지문, (나) 정답 메시가 닫힌 한 덩어리, (다) 오류 없는 과제에서 렌더한 정답 마스크와 정답 메시 투영의 IoU ≥ 0.99(정면·옆), (라) 오류 주입 과제는 주입한 뷰만 정답 메시 투영과 달라짐(그 뷰 IoU < 0.97, 다른 뷰 ≥ 0.99).

### 7.2 첫 걸음 결과(2026-10-30)
- **PNG: PASS**(그림 3장, Blender 가 읽은 화소가 칸 단위로 같음).
- **채점기 대조: PASS**(M0 K1 재채점 10줄 모두 허용 차 안). 처음엔 몸 수만 달랐다(Rust 2~9 대 trimesh 4~14) → trimesh 처럼 '정확히 면 둘이 공유하는 변'만 이어 같아짐.
- **생성기 v2**: (가) 같은 지문 **PASS**, (나) 닫힌 한 덩어리 **PASS**(처음엔 몸 31 → 72: 경계가 격자점에 아주 가까울 때 이웃 변마다 거의 같은 점이 생겨 저장 뒤 합쳐짐 → 그 격자점을 꼭짓점으로 공유하게 고침, `mesh.rs`), (다) **FAIL**(정답 마스크 대 정답 메시 투영 0.982/0.988 < 0.99), (라) **FAIL**(오류 주입 옆 0.951·0.969 < 0.97 은 맞음, 정면 0.983 < 0.99).
- (다)·(라) 원인 진단: 정답 메시가 아니라 **채점기 투영의 치우침**. 같은 정답 메시를 채점 칸 0.01H(=1px) 로 비추면 모델에만 있는 픽셀 261·도면에만 0(가장자리 1px 줄, 다리·뿔), 0.005H 면 0.9965/0.9976, 0.0025H 면 다시 0.989. 칸마다 3x3 점을 찍는 투영이 가장자리를 부풀리고 그 정도가 칸과 픽셀의 정렬에 따라 달라진다. 내 첫 가설(부위 경계 픽셀이 마스크에서 빠짐)은 틀렸다(고쳐도 0.9823 → 0.9824, 고친 것은 맞는 일이라 둠).
- **영향**: 지금까지의 모든 실루엣 점수(파이썬·Rust 같음)가 가는 부위가 많을수록 낮게 나온다. 모든 방법에 같은 방향이라 비교는 유지되지만 절댓값 0.98 근처가 천장이다.
- 다음(기준을 먼저 적고): 채점기 투영 v2 = 칸 기둥의 실제 사각 발자국이 픽셀을 덮는 넓이가 절반 이상이면 칠함(정답 마스크의 '절반 이상' 규칙과 같게). 새 기준: 같은 정답 메시에서 칸 0.01·0.005·0.0025H 모두 IoU ≥ 0.99, 바꾼 뒤 M0 장부를 새 판으로 다시 매기고 옛 값과 나란히 남김.
